# 简历智能解析系统（resume-system）

基于 Spring Boot 的简历智能解析与检索系统，核心是“OCR + 大模型”两级流水线——把 PDF / 图片简历自动转成结构化字段（姓名、联系方式、教育经历、工作经历、技能标签），并支持多维检索。

## 技术栈

| 层 | 技术 |
| --- | --- |
| 框架 | Spring Boot 4.0.1 · MyBatis · Java 17 |
| 存储 | MySQL |
| OCR | 百度 OCR（图片 + PDF 文字识别） |
| 大模型 | 通义千问（结构化信息抽取） |
| 文档处理 | PDFBox |
| 前端 | HTML / CSS / JavaScript（原生） |
| 部署 | Docker |

一句话技术栈：Spring Boot、MyBatis、MySQL、Docker、百度 OCR、通义千问大模型、PDFBox、HTML / CSS / JavaScript、RESTful API 与 JSON 交互。

## 核心链路

```
上传简历（PDF / JPG / PNG）
  → 落盘备份 + 读字节
  → 建记录（status=处理中）
  → 异步线程：OCR 提取全文 → 千问结构化解析
  → 回写数据库（status=成功 / 失败）
  → 按技能、性别、年龄多维检索
```

## 难点与我的做法

### 1. 大模型输出不可控，怎么让它可靠

这是整个项目最核心的问题。千问返回的 JSON 不稳定：年龄字段可能是 `25`、`"25岁"`、`25.0`，甚至干脆不返回。直接反序列化，一个脏数据就能让整条解析失败。

我用“Prompt 约束 + 结果防御式解析”两层兜底：

- **Prompt 约束**：明确要求返回纯 JSON，给出字段模板和注意事项，限制输出形态；
- **防御式解析**：逐字段做类型规范化——性别统一成“男/女/未知”（兼容“男性/Male/male”），年龄无论 Integer / String / Double 都用正则抽数字、再校验 0~100 范围，非法值兜底成 null。

这样模型偶尔抽风，系统也只是某个字段为空，不会崩。

### 2. 第三方 OCR 的 Token 管理

百度 OCR 的 access_token 有有效期，不可能每次识别都去换。我做了三个处理：

- **缓存**：`cachedAccessToken` + 过期时间戳，未过期直接复用；
- **提前过期**：过期时间往前拨 5 分钟（`expires - 300`），避免临界点拿着快失效的 token 去调用；
- **并发控制**：`synchronized` 锁住换 token 的方法，防止多请求同时触发刷新。

### 3. PDF 有“文字版”和“扫描件”两种

PDFBox 只能抽文字版 PDF 的文本，扫描件是图片、抽出来是空的或极少。我用“抽出文本量”判断：少于 100 字符就认定是扫描件，改走 OCR。否则扫描件简历会被解析成空。

### 4. 外部 API 的容错

OCR 和千问都是网络调用，会超时、会限流。解析加了 3 次重试、间隔递增（1s → 2s → 3s），三次都失败才抛业务异常，避免偶发抖动被直接判失败。

### 5. 异步处理与状态机

上传接口不能同步等解析完（OCR + LLM 要好几秒）。我把流程拆成异步：先落盘建记录（status=1 处理中），后台线程解析完更新为 2（成功）或 3（失败），前端轮询状态即可看到进度。

## 搜索与多维检索

支持按技能关键词、性别、年龄区间检索，带分页和排序。排序字段做了白名单校验（只允许 name / age / createdAt），防止把用户输入直接拼进 SQL。

## 构建运行

- 环境：JDK 17 + Maven，`mvn spring-boot:run`
- 依赖：MySQL（用 `init.sql` 建库建表）、百度 OCR 与通义千问的 API key（`application.properties`）
- 部署：`docker build` 生成镜像
